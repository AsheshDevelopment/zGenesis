# Session ownership and native zone authentication

Implemented 2026-10-24. This adds authoritative ownership transactions and a
native authentication socket to the Rust zone worker. Owned Mandara FIRST/status
entry and Chakra/learning requests are now implemented through the native-equation
component. Owned native cell movement and same-endpoint reconnect are verified.
**Nearby actor/NPC simulation and connected client acceptance remain open.**
The overall handoff/gameplay checklist remains open.

## Native zone entry

In a deployed server tree containing the shared DBSRV profile, starting a zone
now requires SQLDMN and DBSRV. Start Server starts dependencies first; the
individual zone Start action does so as well. An isolated management-only tree
without shared profiles retains its earlier administration-only behavior.

The zone validates its native dataset, binds its configured localhost game port,
registers a random boot identity and accepts the remake's normalized native
character packets. The native socket carries `0x1003` authentication and the
existing roster/create/delete requests. Zone requests pass through DBSRV's
protected coordination endpoint to the sole SQLDMN writer. The original
encrypted client stream/internal SSP binary protocol is not claimed.

Empty-character authentication enters roster selection. Nonempty-character
authentication binds an owned character to this zone instance and connection
attempt. The native client needs no additional public ticket packet. Roster
ownership can be fenced atomically when point-02 login races the old socket's
EOF release; a playing/world owner is never replaced through that shortcut.
Delayed release from the old roster token cannot delete the new owner's lease.

Both zone boot identities and connection attempts are generated by the server.
Retrying the same authenticated operation on the same attempt returns the same
lease; another connection receives a duplicate-owner result. Bound sessions
cannot save a different account slot or create/delete roster entries.

Initialized character connections renew their lease every five seconds through
DBSRV/SQLDMN without changing snapshot revisions. A transfer or lost/expired zone
owner rejects renewal. Character state changes use the separate revision-checked
Save operation; unchanged status/lease ticks do not create snapshot revisions.

The ownership label `playing` means ownership of a selected character snapshot;
it is not a gameplay-readiness signal. Zone administration reports
`game_listener_bound=true` but **`game_ready=false`**. Native web availability
therefore continues to report these worlds unavailable. Zone01 accepts the
bounded FIRST/status path when authored tables are staged; unsupported entry
modes and world operations fail closed. See [status authority](NATIVE_STATUS_AUTHORITY.md).
HTLauncher remains connected to its existing offline authority.

## SQLDMN transfer state

Schema 4 retains accounts, native snapshots/revisions, cargo and existing roster
sessions. It adds zone-instance metadata, bound-character/session context and a
durable handoff journal. The migration is tested against an actual schema-3
session-table shape, including saved money, cargo and revisions.

| Internal operation | Guarantee |
| --- | --- |
| Register/heartbeat/unregister zone | A live boot identity cannot be replaced; expired or retired identities cannot save through old sessions. Zone leases expire after 30 seconds and the gateway renews every 5 seconds. |
| Authenticate/bind/load character | Same-endpoint binding and reconnect authentication select only owned characters; connection-attempt retries do not create another owner. |
| Begin handoff | Commit the source snapshot/revision and reservation in one SQLite transaction; fence source writes immediately. |
| Retry begin | Identical request IDs return the stored result without a second save; changed payload/revision/destination is rejected. |
| Claim handoff | Require valid account proof, the selected character and the reserved destination boot identity; rotate the session token atomically. |
| Cancel | A live source can resume its committed snapshot; repeat cancellation does not reapply the save. |
| Expire/restart | Release stale reservations after destination loss/timeout, preserving the latest committed progression for reauthentication. |

Pending reservations last at most 60 seconds while their destination remains
registered. Source disconnect or source restart after commit does not discard
the reservation. Destination restart fences the old reservation rather than
letting another boot instance claim it. Claimed/cancelled journal entries provide
idempotency history and do not prevent later native character deletion.

These are internal authority operations. The client does not supply SQL tokens,
boot identities, connection attempts or handoff request IDs. Portal rules,
destination spawn/entry modes and live cross-zone gameplay
still need their own implementation and tests.

## Shutdown and remaining operational work

The zone stops accepting traffic, wakes its clients, releases their leases and
unregisters its boot identity before completing shutdown. The manager refuses
shared-service Stop while a native zone is responding as bound. If coordination
fails, the gateway fails closed; expiring leases fence stale owners.

Dependency protection when administration itself is unreachable, production
capacity/backpressure, native keepalive, remote security, backup/restore and more
fault/retry coverage remain part of the open operational checklist. The current
gateway is a bounded localhost development implementation (32 connections).
